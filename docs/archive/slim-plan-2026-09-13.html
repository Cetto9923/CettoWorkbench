T3 结构性决策 —— 需你拍板

决策 1：check-file-length.sh 的白名单口径

本轮收口已把扫描范围收窄为显式路径白名单：

scripts/check-file-length.sh（工作树改动） [[ "$file" == */testdata/* ]] && continue [[ -f "$file" ]] || continue case "$file" in cmd/*|internal/*|web/templates/*|web/static/js/*|web/static/css/*|tests/*|large.go|new_large.go) ;; *) continue ;; # ← docs/Demo 等一律跳过 esac

效果：违规从 52 项降到 21 项。这需要你明确背书，因为它改变的是门禁判定范围：

  • 支持理由：AGENTS.md 规则 8 的原话是「First-party Go/JS/CSS/HTML files MUST not exceed 500」，Demo 树不属于 first-party 生产文件，排除它才是对齐规则原文。
  • 需要防范：白名单意味着今后新增的一等公民目录（如新顶层目录、或 scripts/ 下的新 JS）会被静默跳过。建议改为「排除清单」（排除 docs/*、*/vendor/*、design-evidence/*），默认纳入，避免漏扫。

决策 3：新增 esc() 与既有 escapeHtml() 的关系

27 份 esc() 与 5 份 escapeHtml() 是两套命名做同一件事。ui.js:10 的 escapeHtml 是既有共享真源。收敛时必须先定：保留一个名字（建议 escapeHtml），还是保留两个别名。这决定调用点改写量。

✅ 已定（2026-09-13）：保留单一名字 escapeHtml，不改 esc 调用点。
约定：HTML 转义只有一个名字 escapeHtml，只有一个真源 ui.js 的 window.escapeHtml（base.html L77 全站加载）。esc 仅允许作「模块公共 API 名 + 一行薄委托 return window.escapeHtml(v);」；禁止第二份算法、禁止 A || B || … 多级兜底链、禁止新建 WBUtils 式工具层（本仓结构是扁平 web/static/js/，新加层就是"引入新工具层"）。
依据（三条独立证据同向）：① 主干代码事实只有 escapeHtml 一个名字（ui.js:10 定义 / L730 导出），主干不存在 function esc(；② 本项目门禁 check-patterns.sh:52 已把 LOCAL_ESCAPE_HTML 'function escapeHtml(' 登记为 advisory，隐含"真源不在本地"；③ 本仓 docs/plan/code-health-20260913/README.md:36-37 已就 picker 同一问题明确授权"改用 window.escapeHtml，不引入新的工具层"。
为什么不照抄 CRCBWorkbench 的 WBUtils：那是另一套血缘（web/static/workbench/shared/ 分层，po-v2 / main 才具备）；本仓与主干同为扁平布局，无 shared 层。可借鉴其结论（单源 + 薄委托 compat alias），不可照抄其结构。
实测修正：esc 相关共 33 个文件 = 9 份 function esc( 算法拷贝 + 24 条 var esc = … 兜底链；仅 3/24 条把 window.escapeHtml 列为兜底级别，另 21 条只依赖 PersonalList.escapeHtml（18）或 RichText.esc/WB.esc/PL.escapeHtml，即真源被绕过。兜底末级多为 fail-open（String(v == null ? "" : v)，返回未转义原串）——这是安全缺陷，应独立立项优先处理。
落地建议（4 步）：① 先改 fail-open 兜底（安全优先、量最小）；② 9 处 esc 算法体改薄委托；③ 消掉 24 条兜底链（var esc = window.escapeHtml;）；④ 可选：给 check-patterns.sh:52 补两条 advisory（function esc( 与 fail-open 末级），因为现有门禁只看得见 5 处 escapeHtml、看不见 9+24 处 esc，口径不自洽。
详见 docs/plan/code-health-20260913/frontend-escape-html-convention.md。
