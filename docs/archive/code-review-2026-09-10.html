3数据库风险专项（工作台 ⇄ 禅道共库）

3.1 写面盘点与合格项

共库写入面：po 模块（受理/交付状态机、催办、评审、星标、通知已读）＋ schedule 模块（排期保存写 zt_story/zt_task/zt_planstory/zt_productplan、版本窗口 CRUD）＋ operationlog 中间件（每次变更一条）。testtask、query、metrics、clarify 均为只读。

合格项：事务内无 HTTP/LLM/文件 IO；updateHomeDemandStatus、SaveDemandReview、UpdateDemandDeliverFull 采用「FOR UPDATE 锁读 → 状态复核 → 带状态谓词的条件更新 → 同事务写 zt_action 审计」的正确模式；催办用 zt_demand 行锁串行化去重判断；无 AutoMigrate/运行时 DDL/权限自授；锁内事务都很短。

3.2 结构性风险（按严重度）

P1DB-R1 · 排期保存事务规模客户端可控，无服务端上限 → 长事务/锁堆积
internal/module/schedule/service_scheduling_save.go:76-95 · form.go:647-656（Validate 无数量校验）
// SaveScheduling：一个事务内循环处理全部 stories × tasks
return s.repo.Transaction(ctx, func(txRepo *Repo) error {
    for _, storyReq := range req.Stories {          // ← 无 len 上限
        storyID, ... := s.applySchedulingStory(...)  // CreateStory+Spec+Action+LinkStoryToPlan
        s.applySchedulingTasks(...)                  // 每任务 CreateTask+Spec+Action+Link...，任务数也无上限
    }
    txRepo.UpdateDemandScheduling(...)               // zt_demand 收尾
})

一个请求可驱动 stories × tasks × (2~4 表) 的行写入全部落在一个事务：100 story × 20 task ≈ 数千行写 + 数千行 zt_action 插入。后果：长事务（undo 膨胀、purge 受阻）、zt_story/zt_task/zt_planstory 行锁长时间持有，禅道侧正常操作被阻塞。违反 database.md 规则 5「开事务前服务端强制批量上限」。

修复：Validate 增加 len(Stories) ≤ N、len(Tasks) ≤ M（按真实环境数据定值并记录依据）；超限直接 422，不开事务。SaveStoryTasks（service_story_tasks.go:259）同理。

P1DB-R2 · 跨模块锁序反转 → 死锁环（需 DB 证据定级）
schedule：repo_scheduling_write.go:334（story 先锁）→ service_scheduling_save.go:90（demand 后锁）
po：repo_deliver.go:192（demand 先锁）→ :244（story 批量锁） · reporeview.go:159（demand 先锁）
T1 排期保存：  锁 zt_story 行 …… 最后锁 zt_demand 行
T2 发起交付：  锁 zt_demand 行(FOR UPDATE) …… 再批量锁 zt_story 行

两个 Workbench 入口对同一需求的加锁顺序相反。并发交叉时形成 T1 持 story 等 demand、T2 持 demand 等 story 的等待环 → InnoDB 检测死锁回滚其一（error 1213）。当前代码无 1213 识别与重试，用户直接收到失败。违反 database.md 规则 4「跨入口锁序必须文档化并统一」。

修复：统一约定「先锁 zt_demand 再动 zt_story」（排期保存在事务开头先 FOR UPDATE 目标 demand 行）；对 1213/1205 定义显式响应。同时按规则 8 在隔离 MySQL 套件补 reverse-order 重叠写用例验证。

P1DB-R3 · 多行更新按客户端数组顺序加锁
service_scheduling_save.go:77-88（stories 循环）· :283-287（tasks 循环）

两个并发排期请求包含重叠 story 集但数组顺序不同时，行锁获取顺序相反 → 互等死锁。database.md 规则 4 明确「Do not lock in arbitrary client order」。

修复：进事务前对 storyID/taskID 集合排序去重（canonicalize），再按固定顺序处理；同时可顺带拒绝同一请求中矛盾重复的 story 动作。

P2DB-R4 · UpdateStory 无归属谓词、不检查 RowsAffected → 重挂载竞态 + 零行静默成功
internal/module/schedule/repo_scheduling_write.go:334-345 · service_scheduling_save.go:46-57
return r.db.WithContext(ctx).Table("zt_story").
    Where("id = ? AND deleted = '0'", storyID).   // ← 无 fromDemand 归属谓词，无 RowsAffected 判断
    Updates(updates).Error

story 归属校验（allowedStoryByID）在事务外加载；事务内 edit/delete story 不做锁读复核（任务路径有 ValidateStoryForTaskMutation，story 路径没有）。story 被禅道侧并发改挂到其他 demand 时，排期保存仍会写入。且 deleted='0' 谓词下零行更新（story 已删/不存在）被当作成功。违反规则 3「事务外校验不是写时保证」「必须定义零影响行」。

修复：edit/delete 分支复用 ValidateStoryForTaskMutation 锁读复核 fromDemand；或 Update 带 fromDemand = ? 谓词并检查 RowsAffected==0 返回冲突。

P2DB-R5 · 取消关注 SELECT→INSERT 竞态 → zt_starinfo 重复行
internal/module/po/repofollow.go:409-428

Count 查询与 Create 之间无事务无唯一键处理：并发双击取关时两个请求都看到 count=0、都插入 followed=0 行。后续 Update 无 LIMIT 会同时更新重复行（状态最终一致但产生脏数据）。违反规则 6「SELECT-before-INSERT 不是幂等」。

修复：改 INSERT ... ON DUPLICATE KEY UPDATE followed='0'（前提：确认 (objectType,objectID,account) 唯一键；没有则先决策补键，不得自动改共库 schema）。

P2DB-R6 · 读写双池的读后写一致性未定义（需部署证据）
internal/module/po/repo.go:22-46（db=只读池，writeDB=主库） · internal/bootstrap/bootstrap.go:198（dbReadonlyOrPrimary）

列表/角标/详情走只读池，写入走主库。SaveNoticeRead（标记已读，写主库）后前端立即刷新 CountUnreadNotices（读只读池）——若只读池为复制副本且存在延迟，用户看到「标记已读但角标未减」。同理影响关注列表刷新。违反 database.md 规则 7「follows/notice 读后写一致性先定义再使用副本」。若生产只读池实际指向同实例则降级为无风险，需部署配置证据确认。

修复：写后短窗口内的自读（角标、本人列表首页）固定走主库，或在响应里带回新计数。

P2DB-R7 · 无效入参静默返回成功的「假成功」模式
servicefollow.go:82-84 · repofollow.go:434-436 · reponotice.go:280-282 · repo_home_actions.go:213-216

多个写方法对 actor 为空/参数非法直接 return nil，客户端收到 success 但什么都没写。规则 14 要求无效请求不得伪装成功。另 homeUserLabels（:213）吞掉读库错误返回空 map，DB 故障渲染成「无标签」而非错误态。建议统一：鉴权缺失返回错误；降级场景显式标注 unavailable。

  • reponotice.go:283-285：SaveNoticeRead 用 WHERE nr.id IS NULL 防重，无 ON DUPLICATE，并发双击可能 1062 报错（仅体验问题）。SaveAllNoticeReads 的 ON DUPLICATE 版本是正确写法，可对齐。
