# UI Audit — light/dark theme consistency (2026-09-10)

> Scope: static CSS + token inventory + component-fixture visual diff for the
> light and dark themes currently shipped in `web/static/css/`.
> Source of truth: [docs/engineering/frontend.md §"Theme Contract"](frontend.md)
> plus Phase-1 rules in [rules-audit.md](rules-audit.md).
> Evidence directory: [design-evidence/theme-compare/](../../design-evidence/theme-compare/).
> This report records findings only; it does **not** authorize any
> business-side edits to existing components. Each fix needs its own scoped
> task with `git diff --check` + `make check` evidence.

## TL;DR

|---|---|---|

| F9 | No CI/automation captures both light and dark on every PR. | **P3** |
| F10 | No `prefers-reduced-motion` policy audited; theme switch transitions are not gated. | **P3** |

The component-fixture render in `design-evidence/theme-compare/audit-light.png`
vs `audit-dark.png` shows the token system works for the well-tokenised pages
(shell, shared-components, personal-workspace, autocomplete, components).

single-source-of-truth pattern.

## 1. Authority and scope

### 1.1 Authority chain

```
AGENTS.md → docs/engineering/ → file-scoped .cursor/rules/*.mdc
                       │
                       └─ Theme Contract (frontend.md §"Theme Contract")
                          is the engineering rule for light/dark.
```

Theme Contract is at
[docs/engineering/frontend.md](frontend.md#theme-contract); it defines the
ten rules reproduced in §2 below. Anything in this report that conflicts
with the Contract is itself a defect.

### 1.2 Scope of this audit

* **Static inventory** — `web/static/css/**/*.css`, including light and dark
  blocks of `variables.css`.
* **Component-fixture visual diff** — a synthetic HTML page that bundles
  the full CSS stack with `data-theme="light"` and `data-theme="dark"` and
  renders the components listed in §3.
* **Existing design-evidence** — `design-evidence/m1/` (PO attention page,
  three resolutions, all light).

Out of scope (require running dev server with live data):

* Page-level screenshots of every PO route (light + dark).
* Networked interactions (toast, modal, dropdown).
* Performance cost of theme switching on cold start.

### 3.3 Component-fixture visual diff

A synthetic page bundles every shared CSS file with `html[data-theme="light"`
and `html[data-theme="dark"` and renders seven component categories:
page skeleton, type scale, semantic badges, priority, done-tag, controls,
attention sum-card. Outputs:

* `design-evidence/theme-compare/audit-light.png` — 1440×variable, light.
* `design-evidence/theme-compare/audit-dark.png` — 1440×variable, dark.

Visual findings the fixture surfaces:

1. **All seven categories render with token-driven colors in both themes**;
   the token system is working for the well-tokenised paths.
2. **`done-tag.gray` in dark is nearly invisible** because the dark-mode
   block (in `done.css`, not the shared system) sets
   `background: rgba(255,255,255,0.05)` and a 0.12-alpha border over a
   `#1e293b` surface — the badge disappears against the section
   background. (Drives F4 / F7.)
3. **`--color-text-disabled` in dark equals `--color-text-secondary`**
   (`#94a3b8`). The disabled button in the fixture is barely
   distinguishable from the default button. (Drives F7.)
4. **Priority P1 in dark (`#fca5a5` on `#450a0a`) clears WCAG AA**, P2
   (`#fdba74` on `#422006`) and P3 (`#93c5fd` on `#1e3a8a`) clear; P4
   is borderline. All are token-driven and do not need page fixes — but
   verify with an axe-core run before claiming "AA in dark".

### 3.4 Existing design-evidence

`design-evidence/m1/` contains three light-mode PO attention-page

`fix(ui)` commits (`a12fbf89`, `a86f3e59`, `6c78a0a7`, `ded3cf35` and

## 4. Findings

### F1 — P0 — `[data-theme="dark"]` selector duplication in six PO pages

Theme Contract §5 forbids copying selectors under `[data-theme=dark]`
solely to swap background/text/border color. The duplication must move
into `variables.css` so each page consumes semantic tokens only.

**Affected files** (`git ls-files`):

```
web/static/css/po/follow.css        49 selectors
web/static/css/po/wb-priority.css   25 selectors
web/static/css/po/po-urge.css       18 selectors
web/static/css/po/home.css          15 selectors
web/static/css/po/notice.css        12 selectors
web/static/css/po/done.css          10 selectors
```

**Sample evidence** — `web/static/css/po/done.css`:

```css
html[data-theme="dark"] .done-tag.gray {
  background: rgba(255, 255, 255, 0.05);
  color: #cbd5e1 !important;
  border: 1px solid rgba(255, 255, 255, 0.12);
}
```

**Fix pattern**

1. Add `--color-done-tag-gray-bg`, `--color-done-tag-gray-fg`,
   `--color-done-tag-gray-bd` to `variables.css` (light + dark values).
2. Replace the `.done-tag.gray` light rule with `background: var(--color-done-tag-gray-bg)`.
3. Drop the `[data-theme="dark"] .done-tag.gray` block.
4. Repeat for every color used in the duplicated block.

Acceptance: `rg "html\[data-theme=\"dark\"\]" web/static/css/po/` returns
zero results for the six files.

### F2 — P0 — `done.css` repeats the same dark selector block

`web/static/css/po/done.css` defines
`html[data-theme="dark"] .done-tag.{gray,success,blue,warning,danger}`
twice — once at L319–343 (header "6. 深色模式状态徽章适配") and again
at L346–. The two blocks have identical selectors and identical
declarations. The second is a leftover from a merge.

**Fix**: delete the duplicate block at L346 onward (everything from
`/* ---------- 6. 深色模式状态徽章适配 (Dark Mode Status Polish) ---------- */`
the second time until the next section header).

### F3 — P0 — `follow.css` carries 242 hardcoded colors plus 49 dark overrides

This is the heaviest offender. The hardcoded colors map roughly to:

| Hardcoded group | Likely semantic token | File location (representative) |
|---|---|---|
| `rgba(99,102,241,0.06..0.16)` indigo washes | `--color-primary` with alpha utility | `web/static/css/po/follow.css` (~30 occurrences) |
| `#1d4ed8` / `#2563eb` | `--color-info-fill`, `--color-info` | scattered |
| `#34d399` / `#10b981` | `--color-success-accent`, `--color-success-fill` | scattered |
| `#fbbf24` / `#f59e0b` | `--color-warning` | scattered |
| `#f87171` / `#ef4444` | `--color-danger-accent`, `--color-danger-fill` | scattered |
| `#0f172a` / `#1e293b` / `#334155` | `--color-page-bg`, `--color-surface`, `--color-surface-hover` | scattered |

**Fix**: a single sweep that replaces each literal with `var(--color-*)`
or with a new shared `--color-follow-*` token in `variables.css`. This
file alone is responsible for the `#fffbea`-style overflow into the 691
row count flagged by `check-file-length.sh` (see
[debt.md §"Baseline snapshot — 2026-09-10"](debt.md)).

### F4 — P1 — dark block missing focus-ring / disabled / overlay alpha overrides

`variables.css` has 122 dark overrides; the gaps below directly degrade
dark-mode accessibility:

| Missing | Effect | Suggested override |
|---|---|---|
| `--focus-ring` (light `rgba(99,102,241,0.25)`) | Focus ring invisible against dark surface | dark `rgba(129,140,248,0.45)` |
| `--color-primary-ring-soft` (light `rgba(79,70,229,0.16)`) | Same as above for hover halo | dark `rgba(129,140,248,0.30)` |
| `--color-success-ring` (light `rgba(34,197,94,0.2)`) | Success state outline fades in dark | dark `rgba(16,185,129,0.35)` |
| `--color-danger-ring` (light `rgba(220,38,38,0.2)`) | Danger state outline fades in dark | dark `rgba(239,68,68,0.35)` |
| `--color-text-disabled` (light `#94a3b8` = dark `#94a3b8`) | Disabled state indistinguishable from secondary in dark | dark `#475569` |
| `--color-success-ring`, `--color-danger-ring` | Halo on success / danger state invisible in dark | already overridden; verify usage |

**Fix**: add the missing six tokens in `variables.css` dark block; add
a contract test in `tests/e2e/theme-runtime.spec.js` that asserts
`getComputedStyle(...).outline` differs from 0 in both themes.

### F5 — P1 — no dark-mode screenshots in `design-evidence/m1/`

Recent commits `a12fbf89`, `a86f3e59`, `6c78a0a7`, `ded3cf35` all touch
PO surface colors yet ship light-only (or no) screenshots. Theme Contract
§10 requires both themes verified.

**Fix**: regenerate `design-evidence/m1/` with a Playwright script that
opens the PO attention page with each theme and stores
`home-claudepo-m1-{1024x768,1366x768,1920x1080}-{light,dark}.png`. The
synthesised `audit-{light,dark}.png` fixtures in this report are a
template; the PR pipeline should call the same script.

### F6 — P2 — badge / priority / done-tag components live inside page CSS

`wb-type-*`, `wb-priority`, `done-tag` are defined in
`web/static/css/po/{home,follow,notice,workboard,demand-detail,po-urge,wb-priority,done}.css`.
A new PO page that needs a "业务需求" badge must re-declare the same
colors. The Stage-2 palette already has
`--color-business-bg/-text`, `--color-story-bg/-text`, …, so the move is
mechanical:

1. Move the selectors into `web/static/css/components/components.css`
   (or a new `components/badges.css`).
2. Replace each literal with `var(--color-<role>-bg/-text)`.
3. Delete the page-CSS copies.

This converts badge duplication into a single shared component and
makes Contract §4 / §5 self-enforcing for future badges.

### F7 — P2 — disabled text collides with secondary in dark

`--color-text-disabled: #94a3b8` is unchanged between light and dark
blocks. In dark, `--color-text-secondary` is also `#94a3b8`. A
`disabled` button looks like a `secondary` button.

**Fix**: assign dark `--color-text-disabled` to `#475569` (or another
`text-disabled` candidate from the design-evidence palette) and ship a
fixture rendering the disabled / default button pair for both themes.

### F8 — P2 — `wb-priority.css` and `po-urge.css` already have the right tokens but still override

`wb-priority.css` defines `--po-pri-1..4-bg/-fg/-bd` in `variables.css`
yet re-paints the same selectors with hardcoded `rgba(...)` colors in
its own dark block. The overrides are redundant — the token already
covers the case.

**Fix**: delete the 25 dark selectors in `wb-priority.css` and the 18
in `po-urge.css`. Verify in the audit fixture that P1–P4 priority
chips render correctly in both themes after the deletion (they should).

### F9 — P3 — no CI captures both themes per PR

Theme Contract §10 only runs at acceptance time, not at PR time.
Currently `tests/e2e/theme-runtime.spec.js` exists but does not gate
PRs.

**Fix**: add a Playwright script under `tests/e2e/` that
1. opens each PO route under `data-theme=light` and `data-theme=dark`;
2. screenshots at three resolutions;
3. fails the PR if any selector contains hardcoded colors that the
   same selector does not use in `variables.css`.

### F10 — P3 — no `prefers-reduced-motion` policy

`theme.js` does not gate transition duration by
`prefers-reduced-motion: reduce`. Users who request reduced motion still
see the same theme-switch fade if any page adds one.

**Fix**: add a media query in `theme.js` or in a global stylesheet that
sets `transition-duration: 0s` when the media query matches.

## 5. Best-practice comparison

| Practice (industry) | Workbench | Gap |
|---|---|---|
| **Single source of truth for theming** (Tailwind, Material 3, Radix Themes) | `variables.css` is the source; six pages bypass it. | F1 / F3 |
| **Token-only color authoring** | Mix of `var(--color-*)`, `var(--po-*)`, and raw hex | F3 / F6 |
| **Accessibility AA contrast in both themes** | No automated check; manual fixture hints at P4 disabled. | F4 / F7 |
| **focus-visible ring** | `--focus-ring` exists in light only | F4 |
| **Per-PR theme regression** | `tests/e2e/theme-runtime.spec.js` is acceptance only | F9 |
| **Reduced-motion respect** | Not implemented | F10 |
| **Component-scoped styles, page-specialised** | Mixed: components own layout, pages own color in PO | F6 |
| **CSS file-size gate** (`< 500`, `< 300`) | `follow.css` 691, `wb-priority.css` over | F3 / F8 |
| **`prefers-color-scheme` listener** | `theme.js` listens, applies `dark` when system is dark and preference is `system` | ✅ |
| **`localStorage` cross-tab sync** | `theme.js` subscribes to `storage` event | ✅ |
| **No `filter: invert(...)` dark-mode hack** | None observed | ✅ |

## 7. Limitations

* Page-level screenshots of every PO route (home, follow, done,
  notice, schedule, board) in both themes are **not** in this audit;
  they require a running dev server. The component-fixture render is a
  surrogate.
* No actual browser interaction (hover, focus, disabled, drag) was
  recorded. The static analysis tells us what is wired wrong; the
  fixture tells us what users will see in the steady state.
* The component fixture was generated with a desktop Chrome
  (1440×variable). Mobile / tablet sizes are not covered.
* No automated contrast measurement — `axe-core` should be added in
  F9 to give a real AA score rather than visual judgment.
