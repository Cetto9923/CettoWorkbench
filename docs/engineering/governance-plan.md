# 员工工作台架构、安全与多 Agent 开发治理计划

> 已保存的原始治理计划，不是当前工程总规范，也不是自动开始所有阶段的授权。
> 现行规范目录见 [spec-index.md](spec-index.md)。执行范围由当前任务及其指定任务卡确定；
> 原计划与后续计划中的 COMPLETE/WAIT 均需核对具体版本和证据，禁止据此重跑已验收卡。

## 一、目标与实施原则

保留现有 Go/Gin/GORM/MySQL SSR 单体，将其完善为职责清楚、可持续迭代的模块化单体，逐阶段关闭本次审查发现的问题。

建立一条轻量开发流程：

**Agent 找到规范 → 明确变更契约 → 实现与测试 → 独立复核 → GitHub CI → 用户验收合并。**

本轮确定：

- GitHub 提交目标为 `Cetto9923/workbench-claude-po`，使用已核验的 `github` remote。
- 不购买 GitHub Pro，不依赖付费分支保护；采用本地检查、GitHub Actions 和人工合并。明确这属于流程约束，不能阻止拥有同等仓库权限的工具主动绕过。
- 用户负责最终验收；Agent 可以开发和独立复核，不自行合并或发布。
- 兼容 Codex、Claude Code、Cursor、Hermes、Gemini。
- 大模型本轮只交付架构与安全规范，不开发 AI 功能、不选择供应商、不引入模型框架。
- 不承诺“永不出错”；验收目标是主要风险有预防措施、错误能被检测、变更有证据、问题可定位和回退。

## 二、分阶段实施

### 阶段 0：统一规范入口，建立准确的问题清单

**交付内容**

1. 保留 `AGENTS.md` 为唯一工程真源，正文只保留关键红线、阅读路径和验收要求。专题细节继续放在 `docs/engineering/`。
2. 扩充 README，说明员工工作台定位、架构、开发启动、检查命令和 Agent 阅读入口。
3. 建立模块索引，记录各模块职责、公开 Service 能力、依赖方向、表归属和测试入口；不为每个文件重复写说明。
4. 为现有共享前端能力建立简短目录：适用场景、调用示例、错误行为和真实引用位置。
5. 核对旧计划与审计稿，纠正失效的真源指向、验收状态、debug 与用户批量事务结论。未跟踪审计稿不直接覆盖或整体提交；将核实的问题归入统一清单。
6. 每条问题记录：编号、触发条件、代码版本、证据、优先级、修复范围、验收条件、状态。修复后关联提交，不保留误导性的旧状态。

**多工具入口**

| 工具 | 实施方式 |
|---|---|
| Codex | 使用根 `AGENTS.md`，检查局部 override 和启动目录是否影响加载。[官方机制](https://developers.openai.com/codex/guides/agents-md/) |
| Claude Code | 薄 `CLAUDE.md` 显式导入工程真源，不复制规则正文。[官方机制](https://code.claude.com/docs/en/memory) |
| Cursor | 增加始终生效的工程入口；现有文件范围规则仅指向适用专题。[官方机制](https://cursor.com/docs/rules) |
| Hermes | 优先使用根 `AGENTS.md`；检查更高优先级上下文是否遮蔽它，不假定会同时加载所有适配文件。[官方机制](https://hermes-agent.nousresearch.com/docs/user-guide/features/context-files) |
| Gemini | 增加薄 `GEMINI.md`，导入工程真源。[官方机制](https://geminicli.com/docs/cli/gemini-md/) |

统一启动协议：Agent 先确认仓库、分支、已有改动，读取工程入口及受影响模块文档，说明允许修改范围和验收命令。历史记忆、个人规则和旧报告不能替代当前项目事实。

**验收**

五种工具分别在新会话中，从仓库根目录及模块目录启动，正确指出工程真源、分层、权限、数据归属和验收入口。记录工具版本和实际证据；无法运行的工具标为未验收，不能仅凭文件存在宣称兼容。

### 阶段 1：修复安全缺口，测试与修复同步交付

**权限与写入**

- 将全部排期路由映射到已有权限：读取使用 `schedule:list`；新增窗口使用 `schedule:create`；保存排期、任务和修改窗口使用 `schedule:update`；删除窗口使用 `schedule:delete`。
- debug 在登录保护之外限制超级管理员；不新增一套重复角色体系。
- 核对权限常量、角色配置和菜单引用，修正不一致标识；不自动为全部员工补权限。
- Service 从数据库核对请求涉及的父对象、现存子对象及目标关联对象。不能信任请求中的 product、story、task、project、execution 等 ID 组合。
- 覆盖 edit、delete-only 和混合批次；任何非法对象导致全批零写入。
- 把窗口“有关联需求不可删除”等已用于页面控制的约束落实到 Service，并覆盖并发关联与删除。
- 检查角色停用、授权撤销及软删除后的权限读取，按真实 schema 过滤失效记录。

**CSRF、配置与敏感数据**

- 将 CSRF 接入实际 HTTP handler 组装链，默认启用；同步验证现有 form 和 fetch 的 token 传递。
- 统一环境配置来源，验证缺失配置、环境覆盖及本地 HTTP/正式 HTTPS 行为。
- Git 内配置改为占位值，部署包不得携带真实凭证；验证环境注入真正生效。
- 已暴露凭证的轮换作为独立外部步骤跟踪，未经实际确认不标为已完成。
- ZenTao 密码兼容隔离在明确边界内，禁止扩散到 Workbench 自有认证；不直接替换算法破坏已有登录。

**验收**

真实路由组装测试覆盖匿名、无功能权限、对象越界、正常授权；Service 测试覆盖伪造关联、非法子对象、delete-only、混合批次和事务回滚。CSRF 缺失/错误拒绝、合法 token 成功。测试必须能让旧缺陷实现失败。

### 阶段 2：落实模块、事务、迁移和日志边界

- 部门 Service 不再持有或操作 GORM；复用现有 Repo 事务回调方式。保留用户批量创建已有事务，修复逐行查重并验证并发唯一性。
- 明确“Service 定义业务与授权，Repo 执行受约束查询”。允许 SQL 执行过滤和聚合，避免为分层把大表计算搬回 Go。
- 跨模块调用使用公开 Service 能力；不直接操作其他模块的 Repo 或自有表。仅对当前真实依赖作必要调整。
- 为高风险写入补充原子性、重复提交和并发冲突契约。复用事务及受条件约束的更新；冲突明确返回，不静默覆盖或盲目重试。
- 迁移采用版本化 SQL 和显式部署记录，移除请求路径及常规启动中的 AutoMigrate 兜底。不自研迁移框架，不未经确认修改 ZenTao schema。
- 审计日志改为有界、可观察的执行方式：记录操作者、对象、动作、结果和请求标识；支持 JSON 业务动作摘要，禁止直接保存完整请求正文。
- SQL 日志不记录敏感参数；补合成敏感值测试。审计落库失败必须可观察，不再静默丢弃。
- 修复 struct tag、格式等明确基础债，处理检查脚本在空基线、无诊断时的正确退出行为。

**验收**

普通启动及请求不执行 DDL；失败回滚、并发冲突、重复提交行为可验证；权限撤销生效；日志不含测试敏感值，日志失败可定位；原始 `go vet ./...` 与格式检查恢复干净。

### 阶段 3：修复性能和前端维护性问题

**数据库**

- 先锁定通知、待办、首页统计和窗口列表的业务契约：范围、计数、去重、排序、分页、空值和未知态。
- 通知改为 SQL 过滤、分页和必要聚合；保持快捷分类与总数口径。
- 待办保留不同对象的业务区别，使用数据库侧过滤、统一排序和分页；不以任意 LIMIT 截断结果。
- 窗口列表改为批量取得工时、需求数及容量输入，消除按窗口增长的 SQL 调用。
- 首页合并可等价的统计，去除重复字典读取；不默认引入缓存掩盖查询问题。
- 记录优化前后的数据规模、查询数、执行计划、耗时和内存；用受控数据扩展验证增长行为。

**前端与文件结构**

- 对已确认重复的 fetch、错误处理、转义、分页和状态展示复用现有能力，逐页面迁移。
- 保留当前 SSR 和高密度页面风格，不重写前端框架。
- 超长文件按真实职责逐项收敛；纯 DTO 等确需保留的例外必须说明原因和退出条件，禁止机械按行切分。
- 认证少量真实能力作为参考示例，不再把整个旧模块指定为万能模板。

**验收**

列表和统计契约保持正确；窗口查询数不再随窗口逐项增长；被修复列表不再全量加载后分页。改动页面完成真实登录交互、视觉、Console/network 和加载资源版本验证。未取得运行证据不得声称性能达标。

### 阶段 4：固化一键检查与 GitHub 交付流程

- 保留 `make check` 为快速统一入口，补规范入口一致性、JS 语法及确定性的架构依赖检查。
- 架构检查不再仅靠文件名和字符串：检查 Handler 绕过 Service、Service 操作 DB、Repo 依赖 HTTP 等明确边界；业务语义仍由契约测试和评审负责。
- 为门禁自身添加小型正反例，验证新违规被拒绝、已有问题修复后可清除基线。
- advisory 保持语义评审性质；本次新增项必须说明是违规、合理例外还是误报，不以总数不变代替处置。
- 集成测试使用隔离 MySQL 和最小合成数据；E2E 使用专用测试账号。不得默认连接开发或业务数据库。
- GitHub Actions 运行同一检查入口；数据库、并发和浏览器测试按变更影响触发，高风险发布执行完整验收。
- PR 只要求简短说明：问题与行为、变更范围、测试证据、剩余风险与回退方式。权限、schema、workflow、baseline 变更显著列出。
- 普通开发任务不得为获得绿灯扩大 baseline、削弱扫描或删除失败测试。
- Agent 独立复核后提交用户验收；用户决定合并。记录 GitHub 远端 SHA 与对应 CI 结果，不以本地提交代替远端证据。

## 三、未来大模型接入规范

本轮只形成架构决策和验收要求，不创建空接口、模型路由器、向量库、Agent 平台或供应商适配器。

确定以下边界：

- **调用边界**：未来 AI 能力通过应用 Service 编排；工具调用复用既有业务 Service，不直接连接数据库执行任意 SQL。
- **身份边界**：员工身份由服务器会话确定。每次检索和工具执行重新验证权限，模型不能指定可信用户身份或扩大范围。
- **数据边界**：默认仅使用批准的内网模型环境；按任务最小化字段，权限过滤必须发生在数据送入模型之前。
- **内容边界**：业务文本、附件、检索结果均为数据，不能覆盖系统指令或工具权限。模型输出必须验证，不能直接成为 HTML、SQL 或执行命令。
- **行动边界**：首个实际 AI 功能默认只读。未来写操作需要展示具体变更并由员工确认；执行时重新鉴权并防止重复执行。
- **可靠性边界**：模型失败不阻断普通工作台功能；定义超时、取消、并发限制、调用预算和审计。
- **结果边界**：业务回答提供可访问的来源；缺少证据时标注未知，不能生成看似真实的统计或权限判断。

未来 AI 功能上线前，必须测试越权检索、跨用户数据混入、提示注入、敏感数据泄露、失效授权、错误工具参数和重复执行。

## 四、接口与验收约定

**接口变化**

- 保持现有页面地址和正常成功响应；权限与 CSRF 修复会收紧不合法请求。
- JSON 请求未登录返回 401，无权限返回 403；并发或状态冲突返回 409，输入校验沿用现有 400/422 契约。
- 本次触及接口统一错误语义，并同步适配调用方；不一次重写全仓响应格式。
- 内部 Service 接收 `context.Context` 和可信 actor；Repo 接收已验证的查询/写入条件，不新增通用 CRUD 或权限引擎。
- 本轮不增加 AI 公共 API。

**最终验收**

1. 五种 Agent 的规范发现有实际测试记录。
2. 本次确认的安全缺口有修复、反向测试和真实接口证据。
3. 基础检查干净，保留的例外有具体原因；不存在未处理却被宣称关闭的高风险问题。
4. 数据库优化有正确性及执行证据，前端修改通过实际浏览器验收。
5. GitHub CI 与交付代码版本一致；用户能够从简短报告判断是否合并。
6. 大模型边界文档可以指导后续开发，但不宣称 AI 功能已经实现。

## 五、执行与默认约束

- 从当前 `Claude-PO` 实际状态继续核对，每阶段形成独立可审阅改动；不直接写 `main/master`，不自动合并或发布。
- 保留已有未提交、未跟踪内容；禁止全仓格式化、批量重构和宽泛 staging。
- 阶段 0 保持精简，完成入口和问题清单后立即推进安全修复；测试随修复交付，不推迟到最后。
- 每阶段结束更新同一份问题清单和验收记录，不建立额外管理平台。
- 缺少真实 schema、业务决策、工具登录或环境时，精确标记对应验收阻塞；继续其他独立工作，不伪造完成。
- 凭证轮换等外部步骤未完成时，单独保留风险状态；普通代码回退不能恢复已关闭的安全缺口。
- 本计划完成标准是架构边界、开发流程和本次问题形成可验证闭环，不是对所有未来代码作零风险保证。
