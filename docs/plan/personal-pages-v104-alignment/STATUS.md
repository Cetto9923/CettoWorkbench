## 已冻结的行为

1. HomeList = HomeActionBase ∩ stage ∩ focus，页面不得跳到 /todos。阶段 Count 保持 HomeActionBase 全量，不跟随 focus 重算。
2. 今日必推是当前动作今天到期或已逾期未完成，不能偷换成待办的仅今日到期。
3. 待我处理根据当前办理责任判定，不等于所有与本人有关的需求。
4. 任一筛选改变回第一页；关键词等作用于服务端完整集合，不能只过滤当前页。
5. 标题、ID、业务办理是三个不同意图；已办只呈现本人正式动作，不能重新生成待办或伪装再次办理。
6. 通知摘要维度可以交叉，分类互斥。分类数与当前 category 查询口径一致，不使用全局通知总量冒充全部分类数。
7. 不通过文案改名、隐藏 Tab 或显示真实但无关联的数字宣称接线完成。

## D1 / D2 本次代码落地及验证边界

- D1：CountKPIBlocked 只统计当前 status=refuse 的个人范围需求，删除历史审批 JSON 和验收超期推断。参考依据为 CRCBWorkbench 的 service_workitem_mapper.go：当前状态映射 phase，再由 deriveRisks 判断 refuse。状态离开 refuse 即不再计入。该实现只覆盖目前已确认的驳回事实，不声称覆盖所有潜在阻塞。
- 首页焦点：`今日必推`、`阻塞`、`超期`、`挂起` 已改为首页按钮，点击只更新 `/home?focus=...`，保留当前阶段并回到第 1 页；`/demands` 在服务端按当前焦点和阶段范围筛选，未再跳转 `/todos`。首页工具栏的显示区间/总数也会随响应更新，避免表格有数据而显示“共 0 条”。
- D2：PUT /notice/read-all 必须携带 JSON `{ "filters": { ...NoticeListReq } }`；缺失 filters、空请求、无效枚举返回 400，不能退化为全量写入。显式空 filters 对应无额外筛选的当前账号全部通知。
- Service 检查 actor 并验证筛选；Repo 在 writeDB 上复用 noticeBaseQuery/applyNoticeFilters，以 INSERT SELECT 单次写入，保留所有条件且不加 LIMIT/OFFSET。已读筛选与未读插入取交集，结果为零；重复键保留原 readAt。并发幂等依赖既有 (notify,account) 唯一约束，部署前须核实真实库存在该约束。
- 前端发送当前筛选快照，防止重复点击；提示明确包含后续页。修复 URL 恢复时丢失 3d、required/none、mail 的枚举不一致。
- 定向 Go 测试检查账号约束、筛选绑定、跨页无 LIMIT、已读与未读交集、缺失/非法请求；JS 测试实际运行通知脚本并检查 URL 恢复、PUT 内容、重复点击和失败恢复。SQL mock 返回的行数不是真实跨页数据效果证据。
- 现有通知 category / needAction 仍沿用历史事件映射，D2 没有把该语义缺陷宣称为已修复。
