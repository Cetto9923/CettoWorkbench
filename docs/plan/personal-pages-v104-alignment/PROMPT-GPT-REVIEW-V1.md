# 审查提词 — 个人页面功能缺口（产品视角）V1

用法：复制下方「提词正文」，并附上同目录 [`DESIGN-BACKEND-GAPS-V1.md`](DESIGN-BACKEND-GAPS-V1.md)。

审查角色设定：**产品方案审查**（页面能力、业务口径、优先级、待拍板项）。\
**不要**审权限体系、操作日志、DB 账号、分层框架、文件拆分——那些交给架构师。

---

## 提词正文（复制区）

你在帮一位**产品经理**审查「PO 个人工作台」五个页面的功能缺口说明（附件 `DESIGN-BACKEND-GAPS-V1.md`）。作者不是架构师；文档只描述用户可见能力与业务口径。

五个页面：首页 `/home`、待办 `/todos`、已办 `/done`、通知 `/notice`、关注 `/follow`。

本轮**明确不要求你评价**：权限/RBAC、操作日志、读写分离/GRANT、Handler-Service-Repo 怎么拆、中间件与会话。这些由架构师另做。

请从产品角度审查：

1. **缺口是否说人话**：N1–N10 是否能让业务方看懂「现在缺什么、用户会痛在哪」？有无把技术细节误写成产品需求？
2. **优先级**：P0 首页口径 → P0 待办接线 → P1 通知真值 → P1 已办详情 → P2 关注，是否合理？若不合理，给出不超过 5 条重排理由。
3. **待办「待接线」**：未接通前保持禁用、禁止假 0——是否足够避免误导？接通后的最小可用标准还缺哪条用户故事？
4. **首页焦点**：默认仅业务需求（W1）是否可先上线？扩展到研需/任务/缺陷时，产品必须先定的字段是什么（一句话）？
5. **通知「待处理」**：要求「现在仍要我处理」而非历史动词——产品验收应怎么点选验证（3 步以内）？
6. **已办详情 N9**：与「查看对象」并存是否会让用户困惑？文案/入口怎么区分更清楚？
7. **关注**：项目报告已有数据时，产品验收清单最少哪 4 项？
8. **WAIT W1–W6**：是否够产品开迭代会？还缺哪条**纯业务**拍板（不要提权限/日志）？
9. **范围纪律**：若研发把权限体系或操作日志做进本迭代，产品应如何拒收（一句话标准）？
10. **总裁决**：`可开产品评审会` / `需改产品描述后再审` / `缺口仍不清`。最多列 5 条必须改写的产品表述。

### 输出格式

每点 1–3 句：

```text
N. YES|NO|PARTIAL
产品风险: ...
建议改写: ...（无则写「无」）
```

不要写代码，不要给数据库表设计，不要给权限模型方案。
