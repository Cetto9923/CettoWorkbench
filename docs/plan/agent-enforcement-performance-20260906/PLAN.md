# Agent 约束闭环与页面性能执行 Plan

状态：计划已编制；治理与优化未实施，运行时基线待采集。先读 [AUDIT.md](AUDIT.md)，再按本文执行。[EXECUTOR-PROMPT.md](EXECUTOR-PROMPT.md) 是交给执行 Agent 的入口。

## 1. 目标、范围与固定决策

目标：让不同 Agent 能定位同一套规范，使违反关键约束的改动有可执行的拦截证据；消除当前首页/看板随数据量增长的无界候选集，建立持续的页面性能回归保护。

范围：规范发现与证据、质量脚本/CI、相关测试、首页/待办/已办/通知/需求看板及其公共查询成本。此轮制定方案，不实施这些生产变更。未来执行授权以具体卡为单位；不因本 Plan 自动执行旧计划已 COMPLETE 卡。

固定架构：保持 Go/Gin/GORM/MySQL SSR 单体；Handler→Service→Repo；不引入 SPA、Redis、搜索平台、通用查询引擎或新 Agent 管理平台。不以重写架构解决尚未定位的慢请求。

固定业务：保持当前有效 PRD 的对象范围、正式动作、阶段口径、收件人、已读状态、角色能力和对象授权。不得用“更快”为理由减小可见集合、改默认时间范围、伪造计数或取消鉴权。

本文只新增工程任务，不覆盖业务文档。旧计划中已完成优化继续保留；旧性能基线只作为历史对比。若最新 PRD 与下面冻结的兼容性口径冲突，将具体差异标为 WAIT DECISION，暂停该业务变更，继续不依赖它的工程工作。

未来大模型接入：沿用现有 `docs/engineering/ai-boundary.md`，当前不开发模型功能。模型工具调用复用 Service 的 actor/权限/事务边界；不得给模型通用业务库 SQL 凭据、跨用户共享结果缓存或跳过写操作确认。模型耗时与工具查询成本分别计量，限流/超时/敏感数据边界纳入未来功能卡，不能用当前 Plan 宣称已经通过模型安全验收。

## 2. 所有卡通用施工合同

1. 读取 AGENTS、engineering 的 architecture/database/frontend/testing/quality、agent-onboarding、对应模块 PRD、旧卡完成证据及本目录；列出具体适用规则与文件。
2. 记录 pwd/root/branch/HEAD/status。不得回退到本文旧 HEAD；若 HEAD 已变，只分析与本卡有关的新差异，刷新卡基线。分支非 Claude-PO 或涉及未知 WIP 冲突则停止受影响修改。
3. 每卡明确 allowed diff；不改本卡外业务；已有 `test-results/` 不删除、不提交。不自动切分支、提交、push、merge，也不触碰公司 origin。
4. 测试 DB 只允许本卡确认的全新隔离实例/库。名称带 test、环境变量存在、localhost 或配置可读，均不等于允许执行 DDL/写入。
5. 业务 DB 只有另行获准的只读元数据访问；优先 SHOW CREATE TABLE/SHOW INDEX。EXPLAIN 需获准；EXPLAIN ANALYZE 实际执行查询，只在确认安全的隔离环境使用。
6. 证据保留代码 SHA、执行时间、环境别名、命令、退出码、实际断言、跳过项；日志不保留密码、DSN、cookie、SQL值和个人/业务正文。业务截图先脱敏。
7. 每卡必须 git diff --check、make check，加卡内必要测试。集成测试被 Skip 不算通过；浏览器未登录、HTTP200、旧截图、静态 Node 测试均不算浏览器验收。
8. 任一必须门禁失败则 PARTIAL/FAILED/BLOCKED BY EXISTING BASELINE。不能增加 baseline、删除断言、改预期值为新结果以取得绿色。
9. 每卡可回退自身变更，不附带 schema 破坏或数据重建。回退操作仍需按实际用户授权执行，不自动覆盖别人的后续修改。

## 3. AE-01：锁住门禁自身，建立规范加载证明

依赖：无。允许修改适配器、onboarding、quality、Makefile、质量脚本及其自测、workflow、本目录证据；不修改业务实现。

实施决策：

- 保留 AGENTS 为唯一工程宪法，适配器只链接。新增一个精简规范/模块索引，记录有效文件、适用范围、替代关系；不复制正文，不建立复杂配置框架。
- Agent 启动报告固定为：实际工作树 SHA、任务范围、已读文档路径与内容要点、相关 MUST、业务来源、数据所有权、验证命令、未知项。路径清单可检查，真实理解由任务测试和评审验证；不能把自我声明称为已强制执行。
- 同一合成小任务分别在实际使用的 Codex、Claude、Gemini、Cursor 等新会话验证；只登记实际测试过的工具/版本。包含规范定位、拒绝扩大文件例外、识别未授权 DB、缺少运行验证不能报 COMPLETE 四项。未使用工具保持 NOT VERIFIED。
- 将 3 个 Node 测试纳入一个失败即退出的 JS 检查入口及 CI；运行门禁自测。正确归类为 JS 单元/行为测试，可迁到 tests/unit/js 并同步引用；真实 E2E 另保留。
- 增加基于可信比较基线的门禁完整性检查：PR 使用目标分支 merge-base 的规范/基线，push 使用可信 before SHA；拒绝上限增大、hard→advisory、扩大排除范围。缺失历史不能默认通过，应明确失败并补足 fetch。
- 允许精确删除已消除的债务、下降行数上限；禁止普通功能提交自行新增/扩大例外。门禁脚本/CI 自身变化必须独立治理评审；PR 作者在同一 diff 写“已批准”不能成为审批证据。
- 为 660→728 情形添加临时仓库红灯用例：即使同时修改文件与工作树 baseline，使用可信旧基线仍失败。另测下降、纯删除、rename、浅克隆、缺失 before、修改检测脚本等路径。
- 平台若不能提供受保护分支/必要检查，明确标注“本地/CI可检查，合并强制未启用”。采取发布者核验确切 SHA+Job+门禁 diff 的流程，不宣称 hook 或 CODEOWNERS 可自行提供不可绕过保护。平台套餐/权限改变单独由用户决定。

验收：已有20项自测保留，新防放宽用例红→绿；JS故意破坏断言时CI失败；正常下调债务通过；新会话加载证据区分已测/未测。AE-01 的平台强制子项可以 BLOCKED，但不能因此隐藏其余可交付改进或宣称全部模型已验证。

## 4. AE-02：隔离测试安全与 story 读取权限核验

依赖：无；可与 AE-01 分批进行。允许测试 DB helper、相关测试、board 的 Handler/Service/Repo 最小修复（仅确认缺陷后），不改 ZenTao schema。

- 在任何连接/建表/删表前解析 DSN，默认拒绝未知目标；拒绝系统库/业务库，要求专用隔离实例、精确库名允许列表和本次测试显式 opt-in。CI service 的固定契约独立声明，不接受从 tracked config 回退读取。
- 库名允许列表是防误用，不是安全沙箱；使用仅具有该隔离库权限的测试账号，并在 seed 前验证库/实例标识。错误只报告类别，不打印原始 DSN 或 driver 携带的凭据。
- 为解析失败、未知主机/库、空DB、业务DB、无opt-in、合法隔离配置建立无需数据库的测试；未知目标在任何拨号前被拒绝。无需为此引入容器管理框架。
- 追踪 StoryID 的路由→Handler→Service→Repo；建立有权 actor、无权 actor、不存在/已删除对象的测试。对象访问范围依据有效 PRD/现有已确认 Service 契约，不能将“跳过团队过滤”自动解释为允许所有故事。
- 若确认权限缺失，在 Service 先执行对象可见性判断，Repo 接收已授权的范围；拒绝时不得读取/返回任务详情。保留合法“查看故事全部任务”的业务能力；若没有明确范围，输出具体 WAIT DECISION，不猜成“本人任务”。

验收：测试辅助程序不会误连未知库；权限负例覆盖直接请求而不依赖 UI；无权请求不会先查询详情再过滤。没有完成授权范围确认，不解锁看板新子节点接口。

## 5. PF-00：当前性能基线与查询预算

依赖：采集只读 HTTP 不依赖 AE-02；隔离 DB seed 必须等待 AE-02 安全子项。允许测试/诊断证据，必要时最小扩展 sqllog；不优化业务代码。

采样页面：`/home`（SSR和随后demands请求分别）、`/todos`、`/done`、`/notice`、`/board/demand`及故事任务抽屉。先核验实际路由，不自行猜测 API；记录运行二进制/静态资源版本，不能只记 git HEAD。

测量协议：

- 使用获准的测试 actor，不要求用户把密码发给 Agent。至少一个小数据 actor、一个大数据 actor和一个无权对照账号。
- 在同一机器、数据快照、构建模式、DB版本/连接池下做前后对比。dev/prod 模板模式分别记录；不要只切换模式就声称完成代码优化。
- 冷启动一次单列；预热5次后每场景30次记录中位数/p95/max/错误率。共享CI只硬断言确定性指标，延迟录制放固定环境避免抖动误报。
- 在隔离环境测试1、5、10并发；不对业务库压测。样本覆盖100/1000/10000候选记录、增长的用户数、200以上根需求和单根大量子节点，以及空结果/深分页/关键词。
- 浏览器记录导航TTFB、首屏真实数据可交互时间、筛选到渲染时间、请求数、传输字节、长任务、Console/network。日志通过request_id归因，分别计鉴权/菜单、业务查询、模板、客户端渲染。
- 复用 SQLRequestContext/sqllog/QueryCounter，统计每请求 SQL 数、总耗时、最慢查询、返回行数。RowsAffected 不是 rows examined；后者只能来自获准的执行计划/数据库指标，不混用。
- 输出表：场景/代码SHA/数据规模/并发/样本数/SQL数/读取行/响应字节/p50/p95/失败数；慢项按累计耗时排序。不仅记录“页面感觉快”。

目标性质：下面是拟定的同机回归预算，不是已测数据或普适 SLA。固定环境目标为列表 API p95≤500ms，首页真实列表可用≤1.5s，筛选结果可用≤800ms；SQL读取本页详情量与pageSize成比例，不与候选总量线性增长。若环境网络底噪本身超出预算，PF-00 必须说明预算分解并提出修订，不能执行者静默抬高。

验收：基线表可复现；每个主路径有固定语义 fixture；无运行环境时卡为 BLOCKED，不以旧基线补齐。仍可继续 AE 卡和已确认结构缺陷的测试设计。

## 6. PF-01：首页统一候选集、SQL分页与统计

依赖：AE-02 的测试安全子项、PF-00基线。允许 po 的 service/servicefollow/repovaluestream、必要 DTO、相邻单元测试及 integration；前端仅兼容既有分页，不重新设计首页。

冻结等价口径：

- 全部对象身份为 `(kind,id)`；重复匹配多个阶段只计一次，展示采用 valueStreamStages 中首次匹配阶段。
- 兼容当前全部列表顺序：阶段顺序优先，同阶段 demand 在 story 前、各类型 id DESC。使用显式阶段优先级和 kind 顺序保证稳定；不能为优化改成全局id或新业务优先级。
- 单阶段独立计数仍按该阶段口径，不能把各阶段 Count 相加冒充“全部去重”。
- 排期/交付混合列表先全局组合排序分页，再查本页详情；所有 user scope、删除/状态条件沿用已确认字段。

实施决策：

- Service 负责确定允许的 actor scope/阶段语义；Repo 构造固定、参数化的候选投影：kind/id/stage_rank/kind_rank。复用小型局部 query builder，不建全项目通用查询引擎。
- 在 SQL 中 UNION/去重选择最早阶段，Count 与 Page 共用候选条件。根据当前受支持 MySQL 的能力使用派生表等兼容语法；未经版本确认不引入仅特定版本支持的窗口函数。
- 最多一次count、一次本页键查询、按kind至多两次详情、一次本页账号映射；Demands业务链路预算≤5次，另记中间件查询。空页不查详情。
- Home用条件聚合/候选去重聚合取阶段与全部计数；KPI复用其真实集合，不能强行合并不同业务口径。阶段+KPI统计预算≤4次 SQL，不含既有版本窗口链路，后者单列预算。
- 移除不再使用的全量ID分页路径，不留下按错误回退到旧实现的隐式分支；纯阶段已有SQL分页继续复用。

验收：多阶段重叠、跨类型同ID、空阶段、跨页边界、超界页、10000候选、删除/无权账号结果与独立预期一致；增加候选数时应用返回的ID行数仍≤pageSize，查询数不随候选增长。故意恢复全量Pluck或内存分页，测试必须失败；仅sqlmock空结果不足以验收。

## 7. PF-02：按需展示名与公共请求成本

依赖：PF-00；与PF-01共用文件的部分顺序执行。允许 user/po 字典读取、必要Service组装与相邻测试；鉴权和菜单改动必须有额外请求链证据。

- 完成本页键/详情查询后收集去重账号集合，批量读取 account/realname，空集合零查询。已办当前操作者优先用已认证 actor 的显示信息，不重新查全体用户。
- 查询只服务展示，不产生新的访问授权。不得为了名称检索先下载所有用户；关键词责任人匹配留在SQL过滤阶段。
- 本页字典读取最多1次；复用现有边界实现一个批量方法即可，不建 DictionaryManager。兼容空名/删除用户既有显示策略，真实查询错误按已确认错误合同处理。
- 菜单是否从JSON请求移除，先确认没有消费者依赖并做HTTP回归。当前权限每请求重读保障撤权时效，禁止直接加TTL缓存；不把超级管理员测量结果代表普通用户。
- 模板prod缓存已经存在；只在测量证明 dev解析/资源stat 为主耗时后另开小修复，不重复实现模板缓存。

验收：用户表从100增到10000但页面仍15条时，读取展示名的行数有界；中文搜索/多负责人/空名保持正确；401/403/撤权不回退。

## 8. PF-03：看板分层加载与完整集合

依赖：AE-02权限核验、PF-00；先完成 PF-01/PF-02 共用边界再改看板。允许 board DTO/Handler/Service/Repo、workboard 前端/模板、对应测试。独立卡，不能夹入首页修复。

- 根节点完整集合包含业务根需求与符合当前业务条件的独立故事。显式组合排序、SQL Count 和分页；默认20、上限100，保留当前根类型展示先后及各类id DESC，增加DTO分页元信息。
- 只返回本页根、孩子数量/必要聚合，不预加载所有子树。展开时加载直接子层；默认50、上限100，显示“加载更多”及真实剩余量；任务抽屉默认20、上限100，支持后续页，不用静默Limit代表全部。
- 服务端过滤先于统计与分页；每个子节点/任务请求重新验证 actor 对父对象的访问权限，不信任前端传入的POAccount/StoryID。具体权限沿用 AE-02 已确认合同。
- 根全局摘要来自完整可见匹配集合，节点进度来自该节点授权子集合；分别标明口径，不能用当前页 rows 代替。纯计数在SQL聚合，不为进度读取任务全文。
- 超过200个根/100个独立故事仍可访问完整集合。当前未支持的业务关联不猜测，记录字段或语义阻塞。
- 抽屉交互拆出职责独立的脚本，恢复遗留 workboard.js 不高于原660行预算；新文件≤500。不要压缩成一行或无职责切块作弊，也不改旧baseline为更大数。

验收：200+根、单根1000+子节点、任务超过一页、无权父节点、深分页、筛选后空页；任一首屏/展开响应最多一页节点；请求数不随子节点数增长。认证浏览器实际验证展开/关闭/重试/分页，记录资源版本，遮罩修复不得回归。

## 9. PF-04：已办/通知定向查询优化

依赖：PF-00执行计划及PF-02。只改已证实热点，不重做已完成的待办/通知SQL分页。

- 已办时间筛选改成参数化半开区间 `[start,end)`。先固定当前DB会话与应用时区的等价边界，周一起始、跨年周、月末、季度、零日期都需样本；若两端时区冲突，应显式决策而非按开发机时区猜。
- List与Summary计数口径保持各自定义；当区间使summary有复用机会时复用，不能把全局累计改成当前筛选数量。
- 通知保留精确收件人判断、已读用户隔离、当前分类计数范围。先测count与page的实际扫描；仅合并语义一致的计数，不为减少SQL混淆QuickView和Category口径。
- 索引仅在真实DDL/现有索引/选择性/执行计划后形成建议，包含表所有者、索引列顺序、冗余检查和写入代价；ZenTao表的DDL变更单列待批准项，不直接migration。
- 不建议对CSV收件人字符串普通建索引来承诺解决成员检索。如果CSV扫描仍占主要时间，把规范化投影单独列为下一期架构决策，说明同步来源/删除撤回/重建/延迟和权限；本卡不建立可能过期的通知权限缓存。
- 只有证明正文传输是主要成本，才提出摘要+详情接口子卡；需锁定查看全文行为和无权访问回归，不能截断数据后宣称等价。

验收：时间边界/关键词字面值/已读隔离/正式动作白名单测试；相同数据下真实计划或扫描量改善，p95满足基线目标；未获准索引只能列建议，不能算已交付收益。

## 10. PF-05：浏览器请求与持续交付验收

依赖：对应性能卡完成。允许受影响页面JS、现有共享fetch/controller、测试与CI；不重新统一全站组件或引入新前端框架。

- 根据瀑布消除重复初始化请求。快速切换筛选复用已有防乱序机制；必要时通过现有controller增加AbortController，客户端取消不等于DB必然立即停止，后端继续传递request context。
- 文本搜索默认250ms防抖；点击时间/阶段立即请求；同一轮只展示最后选择的结果。不要为每个点击并行预取所有Tab。
- 失败与空数据分开，统计失败不显示0，取消请求不弹错误Toast。登录过期、403和500保持现有HTTP/共享错误合同。
- 在已有浏览器工具或现有项目测试设施下验证真实认证流程。若仓库没有可复现浏览器runner，先记录准确人工/工具步骤与产物，不将Node mock改名伪装为E2E；增加runner应是单独可审查小变更。
- 对功能/规则修改，CI强制确定性测试、SQL数量/读取行数上限、跨用户负例；固定环境记录延迟趋势，不用CI机器抖动替代性能判断。
- 交付记录当前代码SHA、运行资产版本、测试输出、同条件前后对比、确切远端Job。发布前另行获取用户授权，不能自动push。

验收：五个页面首屏及最慢操作均有认证浏览器证据；不出现重复提交/过期结果覆盖/伪空态；每个已承诺性能预算都有测量或明确失败原因。没有通用“高枕无忧”认证，每次改动仍需相应门禁。
