# PO 工作台重构计划

## 目标与边界

本重构从内网仓库 `origin/main` 独立演进。`CRCBWorkbench/po-v2` 只提供已确认的视觉语言和交互参考，不合并其 Git 历史，不复制其单页巨型脚本，也不让其业务口径覆盖本仓库的真实代码、数据库和权限模型。

所有页面继续遵守本仓库的 Go SSR 架构：路由与参数在 Handler，业务与对象权限在 Service，查询与持久化在 Repo，模板只消费明确的页面数据，页面脚本只负责交互和渲染。

## 每页固定流程

1. 盘点 Main 的路由、模板数据、Service、Repo、SQL 和权限边界。
2. 对照 `po-v2` 只提取页面信息架构、组件几何和交互方式。
3. 先定义可验证的页面数据契约；Main 无真源的数据不展示为真实指标。
4. 用最小文件集实现，优先复用全局 token、布局和组件。
5. 执行 Go 测试、静态契约检查、HTTP 冒烟、真实浏览器交互和视觉复核。
6. 每页单独提交；失败或未验证的页面不得标记完成。

## 里程碑

### M0 跨工具规范入口

- 增加 `AGENTS.md` 与 `CLAUDE.md`，只指向 `.cursorrules` 和 `conventions.mdc` 真源。
- 不复制第二份业务规范，避免规则漂移。

### M1 首页

状态：`verified`（2026-09-03）。全仓 `go test ./...`、JS 语法、真实接口、阶段切换、1366×768 与 1920×1080 视觉/几何均已验证。`go vet` 会被 Main 既存的 `internal/model/basemodel.go` struct tag 语法问题阻断，未在首页任务中扩大修复范围。

- 保留 Main 的 `/home`、`/demands`、PO Service/Repo 和版本窗口契约。
- 重构为紧凑页头、十阶段价值流、统一行动列表、版本窗口和数据来源区。
- 删除固定为 0 的今日必推、阻塞、超期、风险和最长天数等伪指标。
- 阶段卡片展示 Main 当前能证明的总数、业务需求数和研发需求数。
- 阶段切换、分页、每页条数、空态和失败态必须真实可操作。
- 禅道链接遵守当前页打开规则。

完成门禁：`go test ./...`、`go vet ./...`、首页契约测试、登录后 `/home` 与 `/demands` 冒烟、1366×768 和 1920×1080 几何检查、视觉复核、Console 无新增错误。

### M2 排期工作台

- 在 Main 现有 `schedule` 模块上收敛页面骨架和交互，不重写已存在的排期 Service/Repo。
- 逐项验证业务需求、独立研发需求、版本窗口和任务维护四条链路。

### M3 需求查询与详情

- 先新增独立模块和对象级只读权限，再实现标准列表与工作台详情。
- 编号进入禅道，标题进入工作台详情；字段必须追到 Repo/SQL 真源。

### M4 我的待办、我的已办、通知与关注

- 四个数据集分别建契约，禁止用同一查询或前端筛选冒充。
- 待办必须由责任人、时间、状态和可执行动作共同判定。

### M5 版本跟进、验收交付、问题风险

- 复用 Main 的版本窗口与禅道对象关系。
- 写操作先落实 Service 对象级校验，再开放按钮和接口。

### M6 专项分析

- 指标管理、指标雷达和质效预警最后开发。
- 只有可追溯定义、范围和数据源的指标才进入页面。

## 状态定义

- `verified`：自动化、真实接口、真实浏览器和视觉门禁均通过。
- `partial`：代码或部分门禁通过，但仍缺真实数据或视觉闭环。
- `blocked`：缺少权限、数据、环境或明确业务决策，无法安全继续。
- `unknown`：尚未审计，不能按 `po-v2` 页面存在推断 Main 已具备能力。
