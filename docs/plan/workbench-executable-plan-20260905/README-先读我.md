# 交给执行模型的入口

本包针对 workbench-claude-po，不是其他同名Workbench仓库。总计划版本2.0，基于HEAD f5f97a42b802b2eadabb393f18a88bb8fcb1aeec。
优先读 [00-执行总计划.md](00-执行总计划.md)，然后只读被指派的 [任务卡](phases/)。
需要单文件上传时用 [完整施工契约.md](完整施工契约.md)。它由相同内容生成，不应与分卡分别编辑。

## 可以直接复制的执行提示词

```text
你负责执行 Workbench 治理计划中的 Phase [填入一个卡ID，例如G1]。
本次仅授权该卡Allowed范围内实现与验证；不授权commit、push、分支切换、部署或真实业务库写入。

先读：
1. 仓库根AGENTS.md与受影响docs/engineering专题。
2. 本交接包00-执行总计划.md。
3. phases/[卡ID].md的全部24项。
4. 已验收前置卡报告和当前git diff。

先输出pre-flight：repo root、branch、HEAD、已有WIP、前置卡、证据是否漂移、允许修改文件、必跑命令。
WAIT卡的推荐选项不是批准。前置未满足时只做卡内明确允许的只读或合成准备，报告阻塞，不猜业务/schema。
只执行这一张卡，不自动开始下一张。

先写能使旧实现失败的有效回归测试，再做最小修复；结果不能只证明mock调用顺序，数据库并发需真实隔离MySQL。
不得为绿灯扩大baseline/削弱rules/删除失败测试；减债仅允许卡内明确列出的精确条目。
完成后按卡第24项报告，逐项附真实命令退出码、旧失败新通过、手工/数据库证据。
缺required环境或验收只能PARTIAL/BLOCKED；不要编造commit SHA、CI run或浏览器结果。
```

## 可以直接复制的独立评审提示词

```text
只读评审 Phase [卡ID] 的实现，不参与代码修改。
读取AGENTS、总计划、完整任务卡和该卡输入/输出SHA及diff。对照24项：
- 业务与权限是否按冻结矩阵，是否把推荐选项当批准？
- 所有改动是否在Allowed，是否改了禁区/baseline/CI来换绿灯？
- 鉴权、查询计数、事务、错误和成功响应是否满足WHEN合同？
- 删除核心修复后哪条测试会失败？有真实旧失败/新通过证据吗？
- 集成是否隔离真实MySQL，实际执行了测试而非0 tests/SKIP？
- 页面/数据库/远端证据是否针对同一代码版本？
- 新抽象是否确有当前需求？有没有整模块重写？
输出每个缺陷：优先级、文件/符号、触发输入、实际/期望、证据和最小修复边界。
不把自测绿灯当独立评审；缺证据明确列出。只能给APPROVE / CHANGES REQUIRED / BLOCKED。
```

## 用户操作顺序

1. 首批建议G0或G1；G1是脚本空基线缺陷，范围小且有明确正反例。
2. 一次交一张卡。WAIT卡先处理对应Decision Gate；没有schema先不要交A0直接修。
3. 实现者给完成报告后，把卡、diff、测试证据交另一个reviewer。
4. 你确认后再单独授权commit/push；查看GitHub对应SHA的CI；最后决定合并。
5. G0后，在你实际会使用的每种工具做冷启动；换版本/插件/启动目录后重新验证。不要把整份完整计划永久塞进每次系统提示，使用总入口+相关卡即可。
6. 最终仍有安全OPEN时不要认为“计划跑完=全部安全”，按总计划验收。

## 文件维护与迁移

本轮产物存储在项目外，仓库原WIP原样保留。未来纳入Git属于G0/独立文档归档范围，先确认要纳入哪些文件；不要宽泛git add。
总计划是执行约束，AGENTS是工程真源；两者冲突应修订计划并明确版本，而不是暗改AGENTS。
修订时只编辑总计划和分卡，再重新生成单文件版；在revision-log记录变化原因、批准决策、受影响卡和新增验收。不能只更新其中一个版本。
source-manifest.json是起点指纹，不含代码或秘密；可供跨模型核对，不是需要永久同步的全仓治理系统。
